# Native host bridge (development only)

The native host runs the player's original 32-bit executable in its own process. A fork of cnc-ddraw supplies the local agent; the existing development page and HD renderer attach to a frame-boundary mirror through the same Worker/shell seam. This is an experimental backend. Offline builds and synthetic tests do not establish the live acceptance gates.

## Build and ownership

On macOS, [the owner launcher](../../packages/native-host/launcher/README.md) provides a single entry point:

```sh
RA2_NATIVE_GAME_DIR="$GAME_COPY" \
RA2_NATIVE_WINE_BOTTLE="$BOTTLE_NAME" \
RA2_NATIVE_WINE="$WINE_EXECUTABLE" \
RA2_HD_CACHE_DIR="$HD_CACHE" \
scripts/remaster/native/play-native.sh --open
```

A configured CrossOver bottle is preferred only after a successful 10-second command probe. Missing, refused, expired or unresponsive CrossOver falls back to the installed free Wine named by `gameres/wine-free/wine-path`, with the launcher-owned `gameres/wine-free/prefix-native` environment. Worktrees find those files in the containing repository. With no explicit Wine executable or scope, the launcher selects that same local free installation. It prints one Chinese line naming the selected runtime. Use `RA2_NATIVE_WINE_PREFIX="$WINE_PREFIX"` instead of a named CrossOver bottle to keep an explicit plain-Wine selection; that choice never silently switches to another runtime. The launcher builds missing local binaries, backs up the supplied copy's existing DLL before replacement, uses two free allowed ports and a fresh token, starts the hidden owned game and loopback page, and prints the exact private URL. `--open` opens Google Chrome; the page automatically selects the supplied YR resources and attaches to that game. The HD options are shared with `scripts/remaster/play.sh` through `scripts/remaster/play-options.mjs`. Exit stops only processes it created and conditionally restores its DLL. It obtains no resources. Native Wine process ownership and browser rendering require a real owner run; build and synthetic lifecycle checks are separate evidence.

Both owner launchers enable the existing single-pass `sr=1` reconstruction for the original menus/dialogs and
original-picture view. It does not run in the HD view's keyed overlay path. The native toolbar omits Quick start:
the page attaches to an existing game process, so the VM startup-page hook cannot open its skirmish setup.

The native launcher's optional `--hd-marks` enables experimental sharp mobile health bars and control-group
numbers for that launch only. It is off by default and sets the existing `native-draw-journal=1` page option
without storing a preference. The start screen and tool panel show a Chinese experiment notice and the exit route:
press Ctrl-C in the launcher, then launch again without `--hd-marks` to turn it off. The existing original/HD
picture switch is unchanged. With the option absent, no draw capture is requested or installed for that new game
process; native requested/installed diagnostics and visible marks still require live acceptance.

The HD web owner entry, `scripts/remaster/play.sh` (or `play.command`), adds `play-start=1` only for ordinary
HD play, including `--menu`; `--train` and `--original` keep their existing startup flow. For example,
`scripts/remaster/play.sh --view classic --print` prints the same gated URL without starting a server or browser.
After resources are selected or restored, its main Fullscreen Start button enters page fullscreen and waits for stable dimensions before measuring; a smaller Window Start button measures the current window. Either choice removes
only `play-start` from the current URL, preserving other query fields, the fragment and history state, before
measurement. A later internal menu-resize reload therefore continues automatically; a new launcher URL always
requires Start again, including in an existing browser profile. No persistent bypass flag is stored. Ordinary
web imports without this explicit parameter are unchanged. Native ready-page reloads instead retain their
launcher-negotiated size and baseline, as described below.

### Film controls

An attached page shows **跳过影片** and **也可以按 Esc** during observed Bink playback outside a visible menu/dialog.
The web route checks actual shell visibility; the native route checks the visible dialog that owns input.
The main menu also plays Bink animation, so an open decoder alone must not offer Escape there. The button sends the ordinary Escape key state and
`WM_KEYDOWN`/`WM_KEYUP` messages. With pointer lock, the first physical Esc releases the browser pointer; press
Esc again to reach the game, or click the button after releasing the pointer. No timed key injection or clock
change is used. Web static and dynamic Bink Open/Close calls retain the same host lifecycle boundary. Native
successful opens and matching closes provide `INPUT_STATE.moviePlaying`, `movieOpens` and completed
`movieTotalMs`, retained from process launch across page attachments. After the same PID, executable identity and
hidden-window validation as menu startup, the launcher also accepts observed successful playback with no visible
input-owning dialog as usable input. It logs film readiness separately in Chinese and releases the page to show
the skip control before the main menu; the existing startup timeout and ordinary menu gate remain unchanged.
Films completed before attachment have no page button; the retained counters measure those completed lifetimes.

### Free Wine and first-run setup

The free-Wine evaluation uses Gcenx/macOS_Wine_builds `wine-stable 11.0_1`. Its bundle declares macOS 10.15 or later, contains Intel 64-bit Wine processes, and supplies 32-bit Windows modules through the new WoW64 mode. Those bundle properties do not establish game compatibility on another Mac. Automatic selection uses the local `wine-path` file and a dedicated `prefix-native` directory. An explicitly selected executable and prefix remain supported; never reuse a CrossOver bottle or run both game backends together.

```sh
unset RA2_NATIVE_WINE_BOTTLE CX_BOTTLE_PATH WINEPREFIX
RA2_NATIVE_GAME_DIR="$GAME_COPY" \
RA2_NATIVE_WINE_PREFIX="$WINE_PREFIX" \
RA2_NATIVE_WINE="$WINE_EXECUTABLE" \
RA2_HD_CACHE_DIR="$HD_CACHE" \
scripts/remaster/native/play-native.sh --open
```

The existing development prerequisites still apply: the player's game copy and HD cache, Chrome, pnpm and the installed local build tools. No packaging or dependency installer is provided. An explicitly selected `RA2_NATIVE_WINE_PREFIX` that is missing or empty is claimed with a private directory-identity marker (the directory's inode; the volume device number is recorded but not compared, because macOS renumbers APFS volumes across restarts), then initialized by `wineboot.exe --init`. Initialization is recorded complete only after the registry and 32-bit registration tools exist and are readable; a partial first attempt is retried while that marker still matches the directory. A prefix selected only through `WINEPREFIX` must already exist. Existing prefixes without the launcher's marker keep the original startup path and receive no preparation or registry repair. Prefix symlinks, invalid ownership markers, and new prefixes in CrossOver bottle roots, including aliases to those roots, are refused. Named CrossOver bottles are probed before selection; a failed probe switches to the separate local free-Wine environment.

The former 2,097,152-pixel area guard bounded the native picture encoder's two RGB565 baselines and the browser
decoder's image allocations; it was not a game-engine or mirror limit. The launcher, agent and decoder now share

baselines use 10,608,960 bytes together, and the conservative picture payload bound is 10,619,296 bytes including

Normal closure uses an already-established authenticated response, not a page-server grace period. Before opening
its native socket, the Worker establishes `GET /__native/session?wait=terminal` and validates its response headers.

flushed. Only then does the launcher close its owned game and page server. A frozen Worker can consume its retained

responses never count as a normal exit, and failure to flush is reported by the launcher after cleanup.

## Binary protocol, version 1

One WebSocket carries requests, replies and streaming updates. All application messages are binary and all integers little-endian. The 16-byte header is `magic:u32 = 0x3142484e`, `version:u16 = 1`, `type:u16`, `requestId:u32`, `payloadLength:u32`. Correlated replies preserve request ID and type; errors use type 13 with UTF-8 explanation. Stream messages use ID zero. Client requests and ACK notifications use nonzero IDs. ACK is a notification without a response.

| Type           | Payload / response                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Hello        | UTF-8 JSON: protocol, pid, gameThreadId, exe `{size,peTimestamp,sha256,verified}`, surface `{width,height,bpp,format}`, limits                                      |
| 2 Read         | Request address, length, expectedFrame; reply frame, address, length, bytes. `0xffffffff` means an unconstrained direct read.                                       |
| 3 Write        | Address, length, bytes; empty success. Restores region protection after writing.                                                                                    |
| 4 Alloc        | Size, preferredAddress, executable; reply address, size. Preferred nonzero must be satisfied exactly.                                                               |
| 5 Free         | Agent-owned allocation address; empty success.                                                                                                                      |
| 6 Subscribe    | rangeCount, ruleCount, maxPages, budgetUs, sampleCount; ranges `(address,length)`; rules `(kind,source,bytes,maxCount,stride)`. Replaces the prior subscription.    |
| 7 Mirror       | frame, flags, pageCount, sampleCount; each page address then 4096 bytes; each independent direct sample address, length, bytes                                      |
| 8 Credit       | Count u32, exactly one; optional negotiated options u32, bit 0 requests draw-journal capture. Asks for the current or next primary-surface picture.                 |
| 9 Picture      | frame, width, height, rowCount; changed rows `(y,encodedLength,segments)`; optional negotiated draw-journal trailer                                                 |
| 10 Input       | kind, a, b, c; kind 1 = postMessage, 2 = key state, 3 = cursor position; empty success                                                                              |
| 11 Diagnostics | Empty request; JSON counters including logicFrames, mirrorBytes, hookUs, hookMaxUs, droppedUpdates, truncation, frameHook and gameThreadId                          |
| 12 Hook        | Boolean u32; enable/disable the version-checked frame hook.                                                                                                         |
| 13 Error       | UTF-8 error; never an assumed success                                                                                                                               |
| 14 Input state | Empty request or u32 flag 1: JSON counters/modal, with controls only for empty. Negotiated u32 flag 2: seven-u32 HCURSOR header plus RGBA, or seven zero words.     |
| 15 ACK         | Frame u32 acknowledging that exact outstanding mirror                                                                                                               |
| 17 Sample      | count, then address/length pairs (up to 16). These direct samples are captured on the logic thread before random samples.                                           |
| 16 Batch       | count; entries address, length, expected original bytes, replacement bytes. All originals must match before any mutation; bounded suspend/patch/rollback operation. |

Follow rules retain the five-u32 layout `(kind, source, bytes, maxCount, stride)`. The optional `hello.limits.followRuleKinds` lists supported kinds. A pointer rule (1) follows the pointer at `source`; a pointer-vector rule (2) follows each object using items at `source+4` and count at `source+16`. A span-vector rule (3) follows the same vector's `(count−1)×stride+bytes` contiguous span. Kinds 4–8 begin with an outer pointer vector at `source`. Kind 4 follows an embedded pointer vector at each parent plus `stride`; kind 5 follows a pointer field at that offset; kind 6 follows an embedded capacity vector using items at member+4, capacity at member+8 and `bytes` per element. For kinds 7 and 8, `stride` packs a first pointer-field offset in its low 16 bits and a child offset in its high 16 bits: kind 7 follows the child's embedded pointer vector, and kind 8 follows the child's pointer field. All intermediate descriptors/fields, pointer lists and final `bytes` blocks belong to the same frame. `maxCount` bounds both outer and inner counts. Null pointers and empty vectors are valid; nonempty vectors require nonnull items. Counts, addresses, arithmetic, total pages and hook time remain bounded; invalid reads become explicit mirror flags or request errors.

Concrete live vectors capture their constructor-verified allocations: Unit `0x8E8`, Infantry `0x6F0`, Building `0x720`, Aircraft `0x6D8`; the house-owned building vector uses `0x720` too. These spans do not skip required pages or change the complete-mirror contract.

The sparse reader working set keeps learned pages individually with separate reader/installer owners. In normal operation, a successful complete cold reader operation replaces that reader's prior footprint; warm cached reads retain its dependencies. Readers refresh their caches once per second. A caught miss cannot retire its own scope, so recovery separately breaks the cycle in which an unreadable learned seed prevents every later complete mirror. An invalid capture, a diagnosed page-capacity fault, or approximately one second without advancing complete state while HD is requested retires all learned/map scopes and reader caches, cancels pending retries by epoch, and resubscribes the fixed policy. A time-budget truncation without an unreadable-range episode preserves catch-up progress instead of repeatedly rebuilding those scopes. Recovery is rate-limited to once per second without a lifetime attempt limit. A confirmed video-mode transition or frame rewind also ends those allocation scopes. Native menus, movies and modal dialogs suspend the liveness watchdog; a return to battle allows a fresh state before declaring another stall.

Recovery preserves the transport's immutable page-delta baseline until the host publishes the replacement subscription revision (or a full reset for legacy hosts), but makes that baseline unavailable to readers. Pending missing-page bookkeeping and previously returned state are discarded. Picture credits and native input remain active. Drawing-control transactions have their own serialized owner, allowing passthrough flags zero to restore original painting even while an HD reader is waiting or the mirror is incomplete. The page retains the last complete HD picture for incomplete or late mirrors. Only a persistent unreadable-range episode or a genuine render failure reveals the live original picture with its Chinese recovery notice; complete state and a usable native frame restore HD. `native.renderHealth.unreadableSinceEpochMs` begins on an invalid-page publication, survives intermediate complete mirrors and subsequent truncations, and clears after a complete render result or an actual battle epoch reset. A successful unit test is not evidence that those pixels, controls, or fade were observed in a real browser.

## Mirror and installer semantics

The adapter owns the socket, sparse pages, request timeouts, frame credits, retry scheduling and destruction. Game policies supply addresses, follow rules, reader factories, speed writes and passthrough installation. YR facts stay under `src/games/yr/`; generic native mechanisms stay under `src/adapter/native/`. No architecture allowlist changes are necessary.

Sparse reads never synthesize zero bytes. `NativeMemoryMiss` subscribes the absent pages. Even if an existing optional reader catches that exception, the operation records the miss, discards the entire result and recreates its reader factories. Reader retries use complete mirror frames; asynchronous direct reads never contaminate the frame image. An installer runs against a private transaction image, buffers every write and restarts the whole operation after fetching absent pages or obtaining allocations. Only a successful complete operation submits an atomic compare-and-write batch. An uncertain commit reply retains executable reservations to avoid dangling jumps.

Attachment at an owned native menu or an observed Bink film becomes ready for pictures and input without waiting for a nonexistent logic tick. It keeps the mirror incomplete and returns null reader results until the game publishes a complete battle mirror. At that point the backend obtains the actual logic-thread ID and verified hook metadata before creating readers or enabling game patches. `awaitingLogicMirror` in native diagnostics identifies this menu/film warm-up state. Attachment outside an owned menu or observed film still requires the first complete mirror within the existing startup timeout; an invalid match stream is not accepted as menu readiness.

`VmShell.getRenderPreparation()` supplies optional asset-loading hints independently of battle visibility and the first logic mirror. The selected game policy performs bounded direct reads of its validated scenario filename, theater and available house identities/colours, then rechecks the scenario identity and house descriptors before publishing. Unknown houses, local player and theater remain null. The VM uses the same field validation while its guest is suspended. These hints may reflect a retained scenario during menus; they may only start speculative resource preparation, never reveal HD, fabricate battle state or seed the coherent mirror. A changed actual map supersedes a speculative load without affecting the original game picture or input.

The YR policy identifies its 800×600 menu video mode. Returning from a different battle mode invalidates render, command and performance reader caches and results. The next battle mode needs a later complete logic mirror before publishing state; a retained prior-match mirror or a read crossing this boundary cannot supply a picture or an input target for the next match. Modal dialogs that keep the battle video mode retain the same match. Frame-counter rollback independently invalidates reader caches.

The development HD asset route uses private browser caching with mandatory revalidation. Its weak ETag includes file identity, size, modification time and change time; unchanged files receive 304, while regenerated files receive fresh bytes. Date-only requests are checked conservatively at subsecond precision. Missing files and stream errors remain uncached. No original asset is added to the production bundle or a shared public cache.

The logic hook validates the pinned executable identity and its full instruction signature before installing a removable detour at the frame counter store. The detour preserves general registers, flags and x87/SSE state. Frame-counter readers validate the actual native detour metadata instead of pretending the patched bytes remain original. Passthrough uses the existing YR installer with an explicit native thread guard, leaving the v86 guard unchanged. Agent-owned stub/data allocations remain alive until process exit; disconnected clients must not leave entry-site patches enabled or erase storage referenced by an in-flight guest call. That teardown restores the original entry sites without a repaint, so a page reloaded during a match would show the previous client's unmaintained terrain cache (key colour, shroud-less strips, terrain from an earlier view position) in the original picture until the game redraws everything. A new NativeCore connection therefore asks the game once, as soon as it is attached to a complete image (otherwise at its first battlefield read), for one full repaint through the passthrough control's `repaint`; every category stays off, and a request made in a menu takes effect at the next battle frame.
