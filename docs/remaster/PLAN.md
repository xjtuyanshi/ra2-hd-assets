## 第一部分：决策摘要（Claude）

### 核心事实

没有一个现成底座能同时做到以下四点：

1. 网页版；
2. 能合法修改；
3. 原版功能完整；
4. 容易做 HD。

每条路都缺一块：

| 路线                                                                     | 原版完整度（第一步）               | 做 HD（第二步）                                              | 合法性                                                   | 主要代价                              |
| ------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------- |
| **RA2 VM**（ra2-games/ra2）：浏览器里用 v86 直接跑你的原版 exe           | ★★★★★ 本来就是原版                 | ★★ 画面全在 exe 内部，要读内存、钩住绘制，再由浏览器重画战场 | GPL-3.0，可以 fork                                       | HD 的"桥接"属于研究级难度，要设止损线 |
| **vera20k**（Rust + wgpu）或 **Vanguard**（TS + Three.js）：开源重写引擎 | ★★ / ★ 缺 AI、战役和大量单位       | ★★★★★ 渲染器在我们自己手里                                   | GPL-3.0，来源干净                                        | 第一步要自己补完大量玩法              |
| **Chrono Divide** 官方                                                   | ★★★★ 遭遇战和联网做得好，但没有 YR | ★★★★ three.js 正交场景，体素已经是网格                       | 闭源，**必须作者书面授权**                               | 结果取决于作者，无法预期              |
| huangkaoya/ts-redalert2 等"开源"仓库                                     | ★★★★                               | ★★★★                                                         | **❌ 由 CD 反编译重建**，上游 LICENSE 自己声明"未获授权" | 不碰                                  |

### 推荐：双轨推进，用证据定底座

- **轨道 A（第一步）**：用 RA2 VM 跑你的正版文件，验证原版功能和性能，也就是 G1、G0 两道关卡。这条路几乎是现成的。
- **轨道 B（第二步，同时开工）**：开发一个**与底座无关**的 HD 渲染器"场景沙盘"。
  - 车辆用实时网格，建筑和步兵用可重新打光的多通道精灵，地形用 PBR，外加水面、雨和爆炸。
  - **第 3–6 周**就能让你看到第一版像样的 HD 画面，并签字定下画面方向（G-Look）。
- **用 1–3 周的桥接实验（G2a）决定 HD 渲染器接到哪个底座**：
  - 桥接成功：接 RA2 VM，得到原版逻辑加 HD 画面；
  - 桥接不成功：转 vera20k 或 Vanguard，把原版玩法补完；
  - CD 作者授权：接 CD。
- 前期的美术资产和渲染器代码**在三条路上都能复用**，这是这套安排的关键。

### 和 GPT-6 Pro 独立方案的对照

**一致的地方（两边各自独立得出）**：

- 不碰由 CD 反编译出来的代码。
- 保持固定投影的混合 2.5D：车辆用实时网格，建筑和步兵用多通道精灵（颜色、法线、深度、阵营色遮罩），地形用 PBR。
- 只有一个权威的游戏模拟；Classic/HD 切换只换渲染器。
- 渲染层只读游戏状态，特效使用独立的随机数。
- 先做垂直切片，再铺开。
- AI 生图只用来定方向，不用来逐帧出图。
- 雾不能泄露敌人信息，性能按帧时间验收。

**分歧**：

- GPT-6 Pro 的首选是**拿到授权的 CD**，公开源码的备选是 **Vanguard**；RA2 VM 只用来对照原版行为。
- 我的看法：
  - 给 CD 作者的信照发，成本为零，但**不能把路线押在别人回信上**。
  - RA2 VM 的桥接确实风险高，所以设了止损线。
  - Vanguard 和 vera20k 两个都保留为备选：vera20k 更完整，Vanguard 是网页版。

**GPT-6 Pro 提出、我采纳进来的几点**：

- 用"模拟状态哈希在 Classic 和 HD 下完全一致"来验收；
- 测试必须能证伪；
- 在仓库里维护 `BASELINE.md`、`RENDER_CONTRACT.md`、`ASSET_SCHEMA.md`、`ACCEPTANCE.md` 四份约束文档；
- 显存预算要尽早算。

### 0. 相比 v1 改了什么

1. **HD 架构改为"宿主接管整个战场画面"（L3-lite）**，不再在原版画面上叠 HD 对象。原版画面只在 Classic 模式下使用，另外用来显示侧栏。
2. **G1 改写**。YR 的哈希门控只卡可选功能（我已核对代码），真正要查的是 exe 有没有 DRM 壳，以及能不能走完启动握手。另外加了一条法律红线：**绝不剥壳**。
3. **新增性能关卡 G0（v86 帧率）和画面关卡 G-Look（第 3–6 周）**。G-Look 用"场景沙盘"提前定画面，和技术风险脱钩，这样你不用等 4–6 个月才看到像样的 HD 画面。
4. **G2 拆成 G2a 和 G2b**，都有时间盒和止损线。工期全部重估：Spike 6–10 周，切片 4–6 个月（精简后的范围）。
5. 事实更正：YR 没有尤里战役；Vanguard 是 11 种类型，不是 11 种单位；YRpp 没有许可证，只能用地址等事实；三处【已验证】降级；引用来源改正。
6. 法律部分补上：**本项目自己也要逆向并钩住 gamemd.exe**；仓库清理清单也补全了。
7. 新增：画面规范（数值版）、捕获范围清单、运动插值、遮挡测试、地形规则、英雄资产由谁来做，以及"AI 概念图里哪些是做不到的"。

### 1. 结论与推荐路线

**推荐底座：RA2 VM**（[ra2-games/ra2](https://github.com/ra2-games/ra2)），**有条件**。它是唯一同时满足以下四点的候选：网页版、GPL-3.0-or-later 可以合法 fork、不是 Chrono Divide 衍生、跑的是原版程序。

**要先讲清楚的准确说法**（替换 v1 里的"一行不改""基本不用做就有"）：

- 游戏逻辑是原版 exe 在跑，但 RA2 VM **已经在运行时打了一小批补丁**，比如 Short Game 判负、修理率修复、启动和战斗跳板、binkw32 指令补丁，YR 还跳过了开场动画。这些补丁都会先校验哈希和指令签名。之后我们的绘制钩子还会再加一些【已验证：代码】。
- 功能是否完整，**目前只在代码层面验证过**：918 个单元测试都不需要游戏文件，真实游戏测试一次都没跑过。战役、长局、8 人对战都没有回归测试，v86 帧率也从没测过。所以"第一步可以直接拿来用"是**有待验证的假设**，不是事实。

**HD 这一步在它上面做，实质是写一个新渲染器**（修正 v1）。CD 系列和 vera20k 在宿主侧已经能解码并画出所有 SHP/VXL/TMP，还没替换的对象可以自然回退到原版画法。RA2 VM 连资源解析器都没有，渲染全在 exe 里面。所以我们要自己补上：浏览器内解码器、原版资源回退渲染器，再加 HD 渲染器。这是选择"合法 + 网页 + 原版逻辑"要付出的代价。

**有利条件**【已验证】：

- 宿主能读取所有 DirectDraw surface（`inspectSurfaceObjects`）。
- 客体没开分页，内存是一整块平坦 buffer，宿主可以直接读。
- YR 1.001 的若干地址与 YRpp 吻合，例如帧计数器 `0xA8ED84`。YRpp **没有许可证**，只能用地址和结构布局这类事实，不能复制它的头文件代码。
- 浏览器内解码器可以复用 Vanguard 的 `@vanguard/formats`：纯 TS、GPL-3.0-or-later、1,954 个测试，和我们的许可兼容。它还带一个 CPU 体素光栅器。

#### 备选：vera20k（[YuriPlanet/vera20k](https://github.com/YuriPlanet/vera20k)）

- **现状**：Rust + wgpu（Metal）重写的 YR 引擎，GPL-3.0，本机构建和 9,564 个测试都通过【已验证】。模拟和渲染强制分离，宿主手里本来就有全部游戏数据，所以 HD 层最好做。
- **切换过去的实际含义**：
  1. Phase 2 写的 TS/three.js 合成器和 shader **基本作废**，要用 Rust/wgpu 重写。
  2. **第一步同样不达标**：AI 是占位实现，没有战役，没有联网传输，核弹、超时空、心灵控制器发射不了。
  3. 不是网页版，移植到 WebGPU 至少要几周（推断）。
- 所以"切换 vera20k"的真实意思是：**先做 HD，原版玩法以后再补**。
- 为了让美术资产在切换后还能用，Phase 2 会先定一份**与底座无关的 HD 资产契约**（见 §4）。

#### 有条件选项：拿到 Chrono Divide 作者的授权

CD 是技术上最适合做 HD 的底座（three.js 3D 正交场景，体素是真正的网格）。前提是作者 Alexandru Ciucă 书面授权，最好附带源码。联系方式：contact@chronodivide.com、Discord、GitHub @use-strict。他以前在 2 小时内批准过一个小请求（mod-sdk issue #7）【已验证】。发信零成本，建议 Phase 0 就发。

#### 否决的候选（要点）

- **huangkaoya/ts-redalert2 及其 fork（DD-Channel、OpenRA2/RA2Web），以及 StillM8**：都是 CD 客户端的反编译重建。上游在 2026-09-03 的 LICENSE 里明确声明不授权【已验证：[commit 898d8918](https://github.com/huangkaoya/ts-redalert2/commit/898d8918)】，代码里有 453 条 CD 字符串，包括 CD 的拼写错误 "alredy"。
- **CD 官方（无授权时）**：闭源，mod SDK 改不了渲染器。
- **TaiYouWeb/ra2**：只是 RA2 VM 的收藏式 fork，落后上游 9 个提交。
- **OpenRA/ra2**：C# 桌面程序，pre-alpha，2026 年没有代码提交，没有战役和 YR。

- **rust-alert/ra2.exe**：不是网页版，"渲染"其实是 CPU 合成整张图，git 提交日期是伪造的。

### 4. 技术架构（修订：宿主接管战场）

**核心**：原版 exe 在 Worker 里的 v86 中运行，负责模拟、AI、联机和存档。

- **HD 模式**：由宿主根据三类数据合成**整个战场视图**：
  1. 从内存读出的状态；
  2. 绘制记录；
  3. 浏览器内解码的原版资产，作为回退。
- 所有对象共用**同一套深度、光照和天气模型**。
- 原版画面只在 Classic 模式下使用，另外把侧栏按整数倍放大后显示。
- 不在拍平的 RGB565 画面上叠 HD 对象。原因：一旦地形、水面或雨由宿主来画，未替换的对象就没法从原版画面里抠出来。这就是 v1 低估了的 L3 问题。

```
┌───────── Web Worker：v86 ─────────┐
│ 原版 gamemd.exe 1.001（你的正版 exe） │
│  模拟/AI/联机/存档 原样运行 + 少量签名校验补丁 │
│  [新] 绘制钩子：先"只记录"，后"记录+跳过"     │
│   → 客体环形缓冲（避免每次绘制一个 hypercall） │
└──┬─────────────┬──────────────┬────┘
   │① 最终帧(Classic/侧栏) │② 内存读取  │③ 绘制记录
   │  postMessage 可转移对象（非 SAB）【已验证】
   ▼
主线程：RenderState 快照（带版本号、与底座无关）
   ├ Classic：现有 vmFrameRenderer（WebGL2）
   └ HD：three.js r186 WebGPURenderer（自动回退 WebGL2）
       ├ 浏览器内解码（@vanguard/formats）→ 原版资产回退
       ├ 地形高度场 + 逐像素材质/水面掩码
       ├ 对象：HD 精灵纹理数组 / glTF 车辆 / 回退原版
       ├ G-buffer → 2D 延迟光照（两个后端通用）
       ├ 水面、天气、VFX、后处理（半分辨率 AO/Bloom/雾 → 一次合成）
       └ 侧栏：客体帧区域按 3 倍整数放大；切片单位的 cameo 用 HD 重绘
```

**捕获范围**（G2 要逐项证明）：

- **绘制类**：SHP、体素、地块，以及非 SHP 的特效类：EBolt（特斯拉电弧）、LaserDraw、RadBeam、Wave（心灵波）、ParticleSystem、Smudge、Overlay（矿石、宝石、墙、桥）、LightSource/Spotlight。这些类名都在 YRpp 头文件列表里【已验证】。
- **每次绘制附带的状态**：半透明度、着色（铁幕红、超时空擦除、隐形/幻影、心控）、阴影绘制、阵营色。
- **从对象内存读**：稳定的对象 ID、**连续朝向**（原版体素只有 32 个量化朝向，直接用会一跳 11.25°）、炮塔朝向、坡面倾斜、HVA 帧、飞行高度、炮口位置（FLH）。这部分要逐个字段逆向，工作量已算进 G2b。
- **战场 UI**：选择框、血条、老兵标记、目标线、路径点、建造网格、集结旗、EVA 文字、迷雾边缘、光标。

**运动质量**：客体的渲染帧率在负载高时会掉，3 倍放大后单位每次移动会跳 3 个像素。宿主要按对象 ID 在客体帧之间做插值，并做平滑卷屏。验收时专门测后期负载下的卡顿，不能只看呈现帧率。

**确定性**：

- 先做"只记录 + 宿主覆盖绘制"，不改客体控制流。
- "跳过原版绘制"作为单独一步，单独做联机不同步测试，因为原版绘制路径可能碰到动画计数器或共享随机数（推断）。
- HD 层使用自己的随机数，不回写游戏。

**分辨率与侧栏**（修正 v1 的算术）：

- v1 的问题：客体 1024×768 是 4:3，面板 3456×2234 约为 1.55:1，两者比例不符。
- 改为客体用 **1152×744**，放大 3 倍正好是 3456×2232，铺满屏幕。shim 支持到 2560×1600【已验证】。RA2 本身接不接受这个分辨率，要在 Phase 0 验证。
- 运行时密度定为 3 倍，母版可选做成 4 倍。
- 侧栏在客体里占固定像素宽度，3 倍整数放大后依然清晰。

**资产契约**（与底座无关，Phase 2 定稿）：

- SHP：按 (SHP 名, 帧号) 查找，KTX2 纹理数组，内含预乘 albedo、视空间法线、高度、粗糙度/自发光、阵营色掩码（调色板索引 16–31）、自发光掩码（索引 240–254）。
- VXL：按 (VXL 名, section) 查找 glTF，枢轴取自 HVA。
- 这样即使切换到 vera20k，美术资产也能照用。

**渲染后端事实更正**：

- three.js r186 的 GTAO、Bloom、Lut3D、SMAA、RCAS 在 `tsl/display` 里【已验证】。
- **ClusteredLighting 在 `examples/jsm/lighting`，只能配合 WebGPURenderer 使用，需要 compute**，WebGL2 回退档用不了。所以光照主方案改成两个后端都能用的 2D 延迟光照。

**性能预算**（推断）：

- 原生分辨率 60 fps，GPU 耗时不超过约 11 ms，全分辨率 pass 不超过 8 个。
- 瓶颈是显存带宽：M5 Pro 为 307 GB/s【已验证：[Apple](https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/)】。
- v86 JIT 会占满一个 CPU 核；Worker 到主线程的传输量还没测过。

3. **G1 一日探针**：
   - (a) 对比哈希：RA2 VM 锁定的 `7b8a0685…`，vera20k 接受的 `1cdd1180…`。
   - (b) **检查 PE 节区里有没有 DRM 壳**（如 `.bind`、`.ooa`）。有壳就停，**不剥**，走 vera20k 或光盘版 exe。
   - (c) 把哈希门控改成 fail-soft，然后从正常菜单启动。
     - 我已核对：YR 只有直达 `?start-page=` 的跳板（`startupTrampoline.ts:29`、`battleStartup.ts:28`）、开发用的 spawner 探针（`spawnerProbe.ts:45`）、性能读取器会在哈希不符时抛错；`networkTiming.ts:33` 不符时返回 false。开场动画跳过会先校验签名，失败时不报错。所以哈希不一致**大概率只会丢掉这些便利功能**，不用把所有补丁重推一遍【已验证：代码】。

### 6. 画面规范（数值版，资产生产前定稿）

- **相机**：正交 2:1（偏航 45°，俯仰 30°），不旋转，缩放范围 1–2 倍。
- **光照**：太阳方向锁定为原版的左上方来光（推断，来自截图观察），曝光固定。
- **LUT 与地图光照**：每个战区一套 LUT。地图 `[Lighting]` 段是调色板域数值【已验证：[ModEnc](https://modenc.renegadeprojects.com/Lighting)】，要拟合成 PBR 光照参数，并按战区用同一场景的 Classic/HD 画面对比平均亮度和色相来校准。
- **阵营色**：规定标准色样；过色调映射后 ΔE 要在阈值内。**先对比测试 Neutral 和 AgX**（AgX 会让高饱和色发灰），我倾向 Neutral（推断）。
- **上限**：规定 bloom 阈值、震屏幅度、HDR 闪光、特效强度的上限；规定单位在复杂地形上的描边或轮廓光规则。
- **装饰性天气**：禁止随机闪电，以免和天气控制器混淆；雾和夜间暗度设上限（原版对战没有战争迷雾）；默认关闭，保持地图原有光照。
- **地形**：
  - 高度场严格复刻 RA2 的离散坡面，否则单位会浮空或陷地。
  - 水、岸、陆地的材质权重由原版 TMP 美术逐像素分类得到，不能按格子算，否则岸线会成锯齿。
  - 悬崖用照原版悬崖做的模块化组件。
  - 城市战区不能硬塞进 8 套材质。
- **水面反射**：只反射天空和网格物体（glTF 船只和车辆），**精灵不反射**。
- **可读性门槛**：
  - 随机抽 20 个单位裁图做盲测，识别率不低于 95%；在后期混战、雨天、夜晚、灰度下都要复测。
  - HD 像素不能超出原版的点击框。
  - 每个朝向的炮口位置要与 art.ini 的 FLH 对齐。
- **遮挡测试**：步兵在 HD 建筑前后、车辆在桥下、飞机飞过建筑、船只靠在岸边悬崖旁。
- **审阅工具**：分屏或划变对比、HD 覆盖率热图、G-buffer 调试视图、黄金存档每周自动截图、闪烁指标。
- **AI 概念图里做不到的**（要事先说清，避免你批准一张做不出来的目标图）：
  - 不重复的独特细节；
  - 夸大的建筑比例；
  - 精灵的倒影；
  - 路径追踪级别的全局光照；
  - 每个镜头单独打光。
- **资产形式**：
  - 车辆：实时 glTF，按连续朝向渲染。
  - 建筑：3D 重建后逐帧预渲染，或者用实时 glTF。
  - 步兵：主力单位用 3D 做 8 方向精灵表；长尾单位用 ControlNet 重绘。
  - 地形：PBR splat 加高度场。
  - VFX：实时特效为主，重头爆炸用 flipbook。EmberGen 官方定价页写着暂不支持 macOS【已验证：[来源](https://jangafx.com/software/pricing)】，Mac 上用 Blender 替代。
  - 屏幕空间 AI 滤镜（如 DLSS 5）不作为最终方案：社区评价是"油腻、糊"【较可能：来自 AI 汇总的评论】，而且只支持 RTX 50。
